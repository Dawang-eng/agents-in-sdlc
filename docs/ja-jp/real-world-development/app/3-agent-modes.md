最初にプロジェクトへ小さな機能を追加しました。より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のワークフローに沿って動作し、適切なものを適切な方法で構築できるように設計されています。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue から新機能を作り、コードが有効で、機能が期待どおりに動作することを確かめ、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使用します。通常は作業対象のファイルの種類ごとに異なるセッションや PR を使いますが、ここでは中心的な概念に集中できるように手順を簡略化します。

このレッスンでは、次の操作を行います。

- GitHub Issue から新しいエージェント セッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードで新機能を実装する。
- コードをレビューする。
- ブラウザー キャンバスで機能を手動で検証する。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がカテゴリーやパブリッシャーでゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、カテゴリーの組み合わせ方など、コーディング前に合意しておきたい詳細があります。Plan モードでこれらの決定を整理し、範囲を限定した実装を Autopilot に任せます。

## 背景

AI コーディング エージェントを開発ワークフローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された Issue を開く。
2. 構築する内容の計画を立てる。
3. コードを実装してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. プルリクエスト (PR) を作成する。
7. コード レビューと継続的インテグレーションが成功したら、コードをマージする。

> [!NOTE]
> チームや組織によって詳細は異なりますが、多くの場合は上記の流れを調整したものになります。

この標準的な手順に従うことで、AI が生成したコードが要件を満たし、人が書いたコードと同じ審査プロセスを通るようにできます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト フィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行する前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、ユーザーの入力を待たずにコードを書き、テストを実行して反復します。

Plan モードで開始して計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選び、リポジトリ上部のナビゲーションで **Issues** を選びます。**Allow users to filter games by category and publisher** を開きます。これはテンプレートに登録済みの Issue なので、新しく作成する必要はありません。
2. **New session** を選び、更新済みの `main` を基にした **new working tree** を選びます。

    ![「New session」ボタンを矢印で示した GitHub Copilot app の Issue ビュー](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択で **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは失敗する場合は、アプリの PATH またはバージョン マネージャーの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てると、Copilot がコードを書く前に方針を確認できます。Issue から開始したため、Copilot はすでに機能リクエストをコンテキストとして把握しています。次のように送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリーとパブリッシャーでの絞り込み、アクセシブルなコントロール、データ アクセスの変更、テストが計画に含まれていることを確認します。複数カテゴリーの組み合わせ方や、該当するゲームがない場合の動作など、不明確な点を話し合います。

計画には、プロジェクトで既に使われているツールによる lint、単体テスト、E2E テスト、型チェックを含めます。フィルタリング機能の実装とテストに範囲を絞り、品質ワークフローを終えるまで PR は作成しません。計画を承認する前に修正を依頼し、後で検証できるよう Issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** (または使用中のバージョンで表示される同等のオプション) を選びます。承認によってモードが自動で切り替わると思い込まず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確かめます。

Copilot が実装を開始します。計画に沿って作業を進め、コードを生成し、テストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まることがあるため、先に計画をレビューしてください。依存関係の不足やポートの競合が報告された場合は、チェック完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、ほかのコードと同様にマージ前のレビューが必要です。コードをレビューしてサイトを実行し、問題がないか確認します。

1. **Changes** を開き、フィルタリング機能の実装とテストを確認します。
2. 複数カテゴリーやパブリッシャーの組み合わせも含めて、結果を Issue と承認済みの補足事項に照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカル サーバーを再利用できます。以前のレッスンではなく、この worktree のサーバーがテスト対象であることを確認してください。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。前と同じようにアプリを起動し、ブラウザー キャンバスでサイトを開きます。

1. 次のプロンプトを使って、アプリを起動し、ブラウザー キャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリーを選び、表示結果が一致することを確認します。フィルターを解除してからパブリッシャーを選び、その結果も確認します。
4. カテゴリーとパブリッシャーを組み合わせ、Issue と承認済みの計画に照らして結果を確認します。複数カテゴリーがサポートされる場合は、合意した組み合わせの動作も検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使って、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンでも同じセッションを使う

フィルタリング機能の PR は、まだ作成したりマージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルタリングのコードに適用し、その後スキルと QA の改善を加えて、レッスン 8 でまとめて PR を作成してマージします。開発サーバーを停止したらセッションをそのままにし、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

- GitHub Issue から新しいエージェント セッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザー キャンバスで機能を手動で検証しました。
